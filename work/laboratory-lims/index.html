Laboratory informatics / Data architecture

Laboratory LIMS Database

A requirements-driven Oracle SQL model for laboratory projects, samples, instruments, employees, and supplies, with relational integrity and audit tracking built into the database.

View repository ↗
Implementation

Oracle SQL · Sequences · Triggers · Views · Indexes

Project stage

Portfolio database implementation

Data context

Synthetic laboratory records

Make sample relationships traceable.

Laboratory records need a consistent relationship to projects, instruments, people, and materials. The project translates documented workflow requirements into a relational model that supports traceability and controlled database behavior.

What I built

  • Represent core laboratory entities in a normalized relational schema.
  • Enforce relationships through primary and foreign key constraints.
  • Use Oracle sequences for surrogate keys and triggers for record history.
  • Provide views, indexes, and representative workflow queries.
Evidence in the repository

What can be inspected.

The repository contains a consolidated schema script, documented requirements, and an entity relationship diagram. These provide a direct path from workflow needs to database structures and representative queries.

Implementation choices.

Requirements before implementation

Business and laboratory workflow requirements accompany the schema and ER diagram.

Enforce integrity at the data layer

Relationships and automated behaviors are encoded in database objects.

Views for common queries

Views expose recurring workflow information without requiring consumers to repeat the underlying joins.

Scope & limitations

Where the evidence stops.

A model using synthetic records in a simulated laboratory context. A REST API and expanded role-based access controls remain future improvements; this is not a deployed commercial LIMS.
